The pipeline is a single 400-line script with no stages. generate.ts does LLM prompting, response parsing, schema validation, temporal validation, TTS synthesis, file I/O, audio copying, props writing, Remotion invocation, and cleanup — all in one async IIFE. Each of those is a distinct concern. If the render fails, you can't re-run just the render without re-running TTS. If TTS fails, you can't retry without re-hitting the LLM. There's no checkpoint system.
The right shape here is explicit stages with saved artifacts between them:
generateScript()  →  output/props/{slug}_draft.json
generateAudio()   →  public/audio_{slug}_{ts}.mp3  +  output/props/{slug}_final.json
renderVideo()     →  output/videos/{slug}_{ts}.mp4

Each stage reads from the previous stage's output file, so you can re-enter at any point with --from-audio or --from-props. Right now you lose all prior work on any failure.
There's no separation between the data contract and the render contract. VideoData is simultaneously the LLM output schema, the Zod-validated type, the props format written to disk, and the props read by Remotion. This means any change to what the LLM should produce requires changing the same type that Remotion reads. If you ever want the LLM to produce a richer intermediate format that gets transformed before rendering, you have no seam to insert that transformation. A VideoScript (LLM output) → VideoProps (Remotion input) split would give you that.
The LLM prompt is doing too much. It specifies the JSON schema, the tone, factual content, image asset paths, language rules, duration constraints, and timestamp format all in one string. When output quality degrades — and it will — you have no way to know which part of the prompt caused it. Separating the schema instruction (structural, stable) from the content instruction (factual, topic-specific) would let you tune them independently and make prompt versioning tractable.
Error handling is inconsistent across the pipeline. LLM failures throw and crash. TTS failure returns null and silently produces a silent video. Render failure throws. Cleanup failure is swallowed. A user running the pipeline has no consistent expectation of what a failure means or whether they need to clean up manually. All stages should either throw-and-exit with a clear message, or return a typed result discriminating success from failure — but not mix the two.
The EdgeTTSProvider now spawns a Python subprocess. This works, but it introduces a cross-language runtime dependency that isn't declared anywhere the Node.js package manager can see. package.json has no mention of Python or edge-tts. A new developer running npm install will get a confusing runtime error. This should either be documented in a PREREQUISITES section at the top of the README, checked at startup with a clear error message, or replaced with a native Node.js alternative (edge-tts has unofficial Node ports) so the dependency chain stays in one ecosystem.
